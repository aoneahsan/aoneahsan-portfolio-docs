A hiring route is easier to choose once you name who will own the decisions after the first release. A demo needs one kind of help. A product with accounts, data and a store listing needs another.

I am Ahsan Mahmood. I build web and Android products, and I direct AI agents as part of that work. These notes are for deciding whether to call me at all. The fuller [comparison on my site](https://aoneahsan.com/compare) shows the shipped work behind each route.

## Start with the job

Write down the smallest outcome you can check in a browser or on a device. Then answer these questions before choosing a supplier:

1. **Does the work need several people at once?** If design, engineering and support must run in parallel under one contract, read the [agency checklist](/compare/agency/).
2. **Can someone already on your team review the code?** A newer developer can be the right hire for bounded work when a senior can make the technical calls. Use the [newer-developer checklist](/compare/inexperienced-developer/).
3. **Are you still testing whether anyone wants the idea?** A generated prototype can answer that without a production build. The [AI-prototype checklist](/compare/vibe-coder/) names what must be checked before you keep it.
4. **Is there one clear deliverable and a short finish line?** A [marketplace freelancer](/compare/freelancer-marketplace/) can be a sensible route, especially when escrow matters.
5. **Will the software need daily attention for years?** Plan for [your own team](/compare/in-house/). An outside developer can build the first release, but should not become the only person who can run it.

The routes can overlap. A founder may use a prototype to test the idea, hire an agency for a fixed date, then employ engineers to own the product. Decide who checks each handover; a change of supplier does not make an untested feature work.

A short brief is enough to begin: what a user must be able to do, what already exists, which accounts and data are involved, and what deadline is real.
